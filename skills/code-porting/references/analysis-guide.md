# 分析指南：源解剖 → 目标盘点 → 熔接面分类

> 三个阶段的产出是方案的原料。宁可多花 token 读源码，不可凭文件名猜结构。

## Phase 1：源工程解剖

### 1.1 扫描盘点

```bash
python <skill>/scripts/port_scan.py <源工程>/<模块根目录> --deps --grep "(_EN|UPINF|LOWINF|_USING)"
```

`--deps` 给出依赖闭包候选；`--grep` 模式按需换（回调名、开关、段名）。

### 1.2 逐文件通读（不跳文件）

- 先读全部 `.h`（接口面），再读 `.c` 的骨架（状态机、表、回调装配）。
- 大文件（>500 行）至少读：头部注释、全部函数签名、状态/迁移表、文件尾的接口表。
- **禁止**只凭文件名和行数推断"这个文件是干什么的"。

### 1.3 提取五类事实（防漏的核心原料）

| # | 事实类型 | 提取内容 | 为什么 |
|---|---|---|---|
| 1 | 接口表 | UpInf/LowInf 函数指针表、装配点、外部回调名 | 移植后链接闭包与生成物耦合点 |
| 2 | 配置开关 | 引用的每个 `*_EN`/`USE_*` 宏，定义在哪个头 | 目标工程要有落点，否则逻辑静默缺失 |
| 3 | 依赖闭包 | include 逐层展开 → RTD 驱动 / EcuAL / 公共头 / 链接段 / mex 外设 / 中断 | A 类清单的边界 |
| 4 | 时序常量 | 与任务周期绑定的宏（如 `X(time)=(time/5)`） | 目标任务周期不同 = 全体错一倍 |
| 5 | 板级真值 | 引脚号/ADC 通道/中断位号/唤醒掩码/器件地址 | 跨板移植必须重算的项 |

### 1.4 git 交叉验证（源是 git 仓库时必做）

```bash
git -C <源工程> log --oneline -- <模块目录>        # 模块全量 commit
git -C <源工程> branch --contains <commit>          # 关键 commit 是否在当前分支
```

- 用户给了 commit 汇总表时逐条核对；没给时用 log 结果自建。
- 结论写明：**当前分支是否已含全部实现**、是否存在只在其他分支的关键补丁（列出，标"可选增强"）。

## Phase 2：目标工程盘点

### 2.1 扫描与对位

- 扫目标工程对应层目录；与源逐目录对位，找同名/同职责文件。
- 重点识别三类：
  1. **空壳/占位**（几十行、状态机只有 INIT→RUN）→ 会被源替换，删前 grep 引用
  2. **TODO 接缝**（`// TODO: 应放进 HSM`）→ 天然熔接点，方案要点名 file:line
  3. **目标已有真实成果**（如目标板专用上电时序）→ **红线，一行不动**，只能"接入"

### 2.2 映射与约束收集

| 收集项 | 用途 |
|---|---|
| 层名/命名映射（`L1_Applications`→`L1_APP` 等） | 纯拷贝的唯一允许改动 |
| DLP 加密文件清单（查 CLAUDE.md/试读） | 实施工具约束：只能 Edit/Write |
| 生成物目录（generate/board 等） | 红线：只走重生成 |
| `.cproject` include 结构、`modules.h` 开关 | C 类修改项 |
| 链接脚本已有段 + ASSERT | 段手术的既有约束 |
| 目标工程编译手段（skill/命令） | §五每步验证列的来源 |
| 目标任务周期、事件表槽位 | 时序常量对齐 + 接线项 |

## Phase 3：熔接面五分类

源依赖闭包中的每一项，归入且只归入一类：

| 类 | 定义 | 目标侧代价 | 典型 |
|---|---|---|---|
| **纯拷贝** | 整目录/整文件照搬，仅 include 层名替换 | 零（新增） | 源业务模块 |
| **薄重建** | 只取源一小部分，接入目标已有体系 | 新增 + 少量引用 | Port 映射宏、单个接口头 |
| **融合** | 目标已有同域代码，合流而非覆盖 | **动目标已有代码** | Service/Board 层同职责模块 |
| **新写** | 源语义 + 目标板级真值重算 | 新增 | 引脚映射表、下电时序 |
| **桩** | 签名与源完全一致、函数体空 | 新增（落点=源同位置，见纪律） | 未启用域的交互依赖 |

分类纪律：
- **纯拷贝最大化**：一项既能纯拷贝又能薄重建时，选纯拷贝。
- **桩宁可多**：调用方存在就给桩，桩不改调用方——后续真实现零成本。
- **桩落点铁律**：桩的落点 = 源符号所属模块在目标工程的对应文件（层名映射后同路径同名）。目标已有该文件 → 函数体追加进既有 .c、声明进既有 .h；目标没有该模块 → 新建同路径文件。**禁止新建"集中桩文件"**（如 `XxxPortingStub.c`）收容散装桩——层错位，破坏源→目标对应关系（实测事故：6125→7255 把 Service_Board 板级 API 桩塞进 App 层 `App_PowerPortingStub.c`）。
- **融合是例外**：全方案融合点通常 ≤3 个，每个必须逐行说明保留什么/接入什么/接缝在哪。
- 新写项必须列出"源依据（file:line）+ 目标真值来源（mex/board）"，禁止凭空写。
