# Code Porting（跨工程代码移植）

## 定位

- **这是移植，不是重写**：源工程代码只做 include 层名替换整体搬入；目标工程已有代码只允许极少数"熔接面"。
- **完整性第一**：移植漏一部分 = 编译过但功能残废。宁可多花 token 读源码，不可凭文件名猜。
- **两段交互，分离产方案与执行**：交互1 只出方案不执行；交互2 才按方案执行。二者通过已批准方案衔接，绝不默认自动执行。

## 两种交互模式（开场先确认用户要哪个）

| 模式 | 目标 | 终点 |
|---|---|---|
| **交互1 生成移植方案** | 输入四参数 → 分析 → 出八段式方案（Plan 批准） | 方案获批即止，**不执行** |
| **交互2 按方案移植** | 基于已批准方案 → 输出 /goal → 逐步执行 | 执行+验证完成 |

- 用户只说"移植 X 到 Y" → 默认走**交互1 出方案**，获批后询问是否进入交互2。
- 用户说"按这个方案开始移植"（指已有方案）→ 走**交互2**。
- 交互1 时禁止提前动手改任何目标工程代码；交互2 时禁止重新分析（方案已是权威输入）。

## 输入（四参数全部需用户手动输入，见 Phase 0）

| 参数 | 说明 |
|---|---|
| 源工程路径 | 参考工程（移植内容的来源） |
| 目标工程路径 | 移入工程 |
| 移植范围 | 模块/目录/功能域边界描述 |
| 用户要求 | 用户对移植的具体诉求/约束/期望 |

写方案（Phase 5）前先通读 [example/6125To7255电源管理移植.md](example/6125To7255电源管理移植.md)——实测交付过的成品方案，对齐其质量标准（决策表粒度、红线表两栏写法、修改清单的 file:line 量化、**§五 Mermaid 执行计划图**）。

## 流程总览（两段）

```
交互1 生成方案:  0 输入确认(四参数) → 1 源解剖 → 2 目标盘点 → 3 熔接面分类+决策
                → 4 防漏校验(不过则回1/3) → 5 Plan 出方案 → 获批即止
                                    │
交互2 按方案移植: (方案已批准) → 6 输出 /goal → 逐步执行 §五 计划(每步验证) → 完成
```

## Phase 0：输入确认（四参数必须全部由用户手动输入，禁止自行推断）

**四个参数，缺一不可，全部来自用户输入，不得猜测/不得从环境或代码推断默认值：**

| # | 参数 | 说明 | 示例 |
|---|---|---|---|
| 1 | 源工程 | 移植内容的来源工程（绝对路径） | `D:\...\6125\FreeRTOS_S32K312` |
| 2 | 目标工程 | 移入工程（绝对路径） | `D:\...\cdc_7255` |
| 3 | 移植范围 | 要移植的模块/目录/功能域，边界要明确 | "电源管理模块（状态机+上下电时序+电压检测）" |
| 4 | 用户要求 | 用户对这次移植的具体诉求/约束/期望（如"只动架构不动实现""宁多花 token""参考某文档"） | "参考《6125To7255电源管理移植.md》，只移植架构，别多改目标工程代码" |

**执行规则：**
- 开场第一件事就是问齐这四项。调用参数带了的（如 `argument-hint` 里的值）只能作为**候选提示**展示给用户确认，不能直接当成最终输入。
- 用 AskUserQuestion 或直接文字提问让用户**手动输入**；若某项用户没给，必须明确询问，不得跳过。
- 四项都拿到后，**逐项向用户复述确认**（含"用户要求"原话），用户确认后才进入 Phase 1。
- 若用户未给出路径但只说了模块名（如"把电源管理移植过去"）→ 列出可选的源工程/目标工程候选路径，请用户指定，不得自己选一个就开工。

## Phase 1–3：分析（→ [references/analysis-guide.md](references/analysis-guide.md)）

1. **源解剖**：`port_scan.py` 盘点 + **逐文件通读**；提取五类事实（接口表/配置开关/依赖闭包/时序常量/板级真值）；源是 git 仓库时做 commit 交叉验证。
2. **目标盘点**：已有骨架/空壳/TODO 接缝（file:line）/已有真实成果（=红线）；层名映射；工程约束（DLP 文件、生成物目录、编译手段）。
3. **熔接面五分类**：每项依赖归入 纯拷贝/薄重建/融合/新写/桩，纯拷贝最大化；需要用户拍板的点收集成决策表，**AskUserQuestion 一次问完**。

## Phase 4：防漏校验（→ [references/completeness-check.md](references/completeness-check.md)）

七维台账（文件/符号/开关/回调/配置/调度/数据），源侧每项事实必须落在三态之一：移植/桩/明确不移植+理由。
**校验不过 → 回 Phase 1/3 补分析，禁止带漏写方案。**
反向校验：§四.C 每个改目标文件的行，必须溯源到台账行号，否则删。

## Phase 5：Plan 模式生成方案（→ [references/plan-template.md](references/plan-template.md)）

- 不在 plan mode 时先 `EnterPlanMode`；已在其内则直接进行。
- 按八段式模板写方案：Context+决策表 / 红线表 / 总体策略 / 修改清单(A新建·B融合·C改既有·D重生成) / N 步执行计划 / 关键执行细节 / 验证标准 / 风险红线。
- **能用图就不用文字**：§五 执行计划必须用 Mermaid flowchart（节点=步骤内容，边=验证手段），状态迁移用 stateDiagram，架构关系用 graph。参考 [example/6125To7255电源管理移植.md](example/6125To7255电源管理移植.md) 的 §五 风格。
- `ExitPlanMode` 请求批准；被拒 → 按反馈修订后重提。
- **获批后即停，不进入执行。** 询问用户："方案已批准，是否进入交互2（按方案移植）？" 用户说"执行"才进 Phase 6；说"只要方案"或沉默 → 停在 Phase 5，交付方案。
- **方案落盘（交互1→交互2 衔接的关键）**：批准后必须把方案写入 `output/<模块名>-port-plan.md`（用 Write，`output/` 已 gitignore）。文件开头含四参数 + 决策表，作为交互2 的权威输入。这是交互2 定位方案的唯一可靠途径。

## Phase 6：goal + 执行（交互2，→ [references/goal-format.md](references/goal-format.md)）

- **仅当用户明确要求执行时进入**（从已批准方案衔接，不重新分析）。
- **定位方案**：先 `ls output/` 列出候选方案文件，请用户指定用哪份；用户也可直接给路径。读该方案全文作为权威输入，方案不存在 → 停，回交互1 先出方案。
- 输出 `/goal` 块（一句话目标 / Scope / Constraints / Done when / Stop if / token 预算），全部从方案推导，并声明"目标方案 = <output/xxx-port-plan.md>"。
- 按 §五 步序逐步执行：每步结束跑该步验证，过了才进下一步；Stop if 命中 → 停下报告差异，等裁决。
- 执行中发现台账外的源文件/依赖 → 停，补方案，不"顺手移植"。
- **清单封闭**：新建/修改任何目标文件前，先核对方案 §四 清单；清单外文件（含"为链接闭合顺手建的桩文件"）一律禁止——缺桩/缺落点 → 停，补方案经用户批准再动（实测事故见全程硬约束 5）。

## 全程硬约束

1. **移植铁律**：源业务逻辑/阈值/时序常量/算法一行不改；目标已有真实成果一行不动；桩签名与源一致、不改调用方。
2. **完整性**：台账三态全覆盖；执行中发现台账外的源文件/依赖 → 停，补方案，不"顺手移植"。
3. **工具纪律**：DLP 加密工程文件（bash/grep 读到 `%TSD-Header` 密文者）只能用 Edit/Write 修改，严禁 sed/echo 重定向/脚本批量替换；生成物目录（generate/board 等）严禁手改。
4. **token 态度**：用户明确"宁多花 token"——逐文件读、七维全查、方案写全，不为省 token 跳步。
5. **桩落点 + 清单封闭**：桩落在**源符号所属模块在目标工程的对应文件**（层名映射后同路径同名；目标已有 → 函数体追加进既有 .c、声明进既有 .h；目标没有 → 按映射新建同路径文件）。禁止在清单外新建"集中桩文件"收容散装桩——实测事故：6125→7255 移植把 Service_Board 板级 API 桩塞进 App 层 `App_PowerPortingStub.c`，层错位，触发用户红线。修改清单必须穷举实施期将创建/修改的每一个文件，实施期不得创建清单外文件。
