# doc-audit 模式:Markdown 文档规范审核与自动整改(当前工程)

> 范围 = **当前工程** 的 `doc\` 目录(会话工作目录所在工程)。按《MCU 嵌入式开发技术文档(Markdown)规范》全量审核,并**直接整改**发现的问题。

## 0. 授权清单(每次审核前先读,2026-11-06 增)

**开工前必读** `<本skill目录>/config/config.conf` 的 `[doc_audit]` 段(缺失则读 `config.conf.example`,再缺失视为三张名单全空);也可直接执行下列命令打印三张清单:

```
python <本skill目录>/scripts/mdmap.py doc-audit-config --repo <工程根>
```

| 键 | 含义 | 命中后的行为 |
|---|---|---|
| `no_claude_md` | 不生成 / 不维护 CLAUDE.md 的目录或文件前缀(与 `[map] exclude` 合并) | 这些路径严禁创建或修改 CLAUDE.md;doc-audit 不碰、claude-md 不建模块 |
| `no_modify_docs` | 完全不允许修改的 doc | **整份跳过**:不浓缩、不补章节、不改版本行、不转图;报告汇总表状态记「按配置跳过」并注明来源为 no_modify_docs |
| `no_canvas_docs` | 允许修改,但**禁止 Mermaid→Canvas** | 只做格式 / 浓缩 / 准确性 / 章节补齐整改;**所有图保持 Mermaid 原样**,禁新建 `.canvas`、禁把流程图/架构图/状态机图转 Canvas |

- 匹配规则:路径相对工程根、正斜杠、大小写不敏感、支持 `*` 通配;目录前缀命中即整目录生效。
- 清单是**硬约束**,优先级高于下文所有图形式要求;与规则冲突时一律以清单为准。
- 报告末尾必须单列「按配置跳过的文档 / 禁转 Canvas 的文档」及其命中的配置键。

## 审核范围与模式:全量审核

- 每轮**递归重新审核当前工程 `doc\` 下所有 .md 文件(含 README.md)**,不依赖历史报告日期或文件修改时间做增量筛选,所有文件每轮全部重新检查。
- 若本轮所有文件均无问题,报告仍需生成,汇总表中记录「0 问题」。

## 评审标准(逐条检查)

### 1. 格式规范
- 一级标题(`#`)全文档仅出现一次(文档标题);标题层级不超六级;代码块必须标注语言(c/shell/mermaid 等);时序参数、寄存器定义、引脚分配必须用表格呈现;文件编码 UTF-8。

### 2. 章节完整性(按文档类型区分严格度)
- **设计类文档**(文件名含「设计/架构/方案/说明书」)必须包含:概述(模块功能、适用 MCU 型号——按工程从根 CLAUDE.md 提取,如 dabbox=HC32F460、CDC_7255=S32K312、文档目的)、硬件资源(引脚/外设映射表)、系统架构(架构图,见 3.4 图形式选取)、软件流程/状态机(流程图/状态机图,见 3.4)、时序设计(Mermaid sequenceDiagram)、寄存器或 API 说明、注意事项、测试验证。
- **使用指南/踩坑记录/工具说明类**文档可豁免硬件资源与时序章节,但必须有概述和注意事项。

### 3. 时序设计(重点章节)与时序图绘制规范
- **3.0 时序信息完整性**:涉及时序的文档必须有时序参数表(列含 参数/符号/最小/典型/最大/单位/来源);总线速率、setup/hold 应标注裕量。
- **3.1 工具与语法**:**时序交互**应使用 Mermaid sequenceDiagram(Markdown 原生支持),保证可维护、可版本控制、无需额外图片资源;用非 Mermaid 形式(截图/外部图片)表达时序图视为不合规。**流程图、状态机图、架构图按 3.4 的复杂度阈值决定用 Mermaid 还是 Canvas**,简单图优先留在 Markdown 里。
- **3.2 绘制要点(逐项检查)**:参与者用 `participant` 声明;信号命名与原理图/数据手册严格一致(如 CS、SCLK、MOSI、CS2/CS3);关键延时用 `Note` 注明参数符号(t_setup/t_hold 等)与数值;异步事件用虚线箭头(`-->>`)表示响应/中断、实线箭头(`->>`)表示主动调用,不得混用;循环/分支(重试、异常)用 `loop`/`alt` 块表达;涉及时钟边沿在 `Note` 中写明采样边沿;时序图中每个 t 参数必须在文档内参数表中定义数值。
- **3.3 原则**:单一职责(一张图只表达一种协议/一个模块);粒度匹配(长流程可合并为框图,通信关键细节逐帧展开);注释完整(重要延时/超时/重试有文字说明);设备一致性(信号名与数据手册一致);双向验证(每个时间参数可回溯 Datasheet 或实测波形)。
- **3.4 流程图/状态机图/架构图:图形式选取与 Canvas 规范(2026-11-06 用户裁定,取代 2026-11-05 旧裁定)**:
  - **总原则:简单图用 Mermaid,复杂图用 Canvas。** 不是所有流程/状态/架构图都要转 Canvas,只有 Mermaid 难以表达清楚的才转。
  - **判定阈值(加权打分,≥4 分才转 Canvas)**:

    | 维度 | 计分 | 说明 |
    |---|---|---|
    | 节点数 | >20 记 2 分;11–20 记 1 分 | 节点过多 Mermaid 自动布局会挤成一团 |
    | 分层/分区 | ≥3 个语义层或分区 记 2 分;2 个 记 1 分 | 需要手工排布色带时 |
    | 跨区连线 | 存在跨层/跨区回环或交叉 ≥5 条 记 2 分 | Mermaid 无法控制线路走向 |
    | 卡片需写多行说明 | 需要「模块名 + 职责」等多行文本 记 1 分 | Mermaid 节点内换行渲染差 |
    | 并行/泳道 | 多泳道或并列分支 ≥3 条 记 1 分 | 泳道图 Mermaid 支持弱 |

  - **必须留在 Mermaid**(得分 <4 一律不转):单链流程(≤10 节点)、简单分支/判断、线性状态机(≤8 状态)、两层结构图、时序交互(始终用 `sequenceDiagram`,永不转 Canvas)。
  - **无条件留在 Mermaid**(不参与打分):命中 `[doc_audit].no_canvas_docs` 的文档(**全部图保持原样**,禁新建 `.canvas`、禁任何流程图/架构图/状态机图转 Canvas)。
  - **Canvas 文件位置**:与 md **不同目录**。在 md 所在目录下新建文件夹 **`<文档名>_canvas`**(文档名去掉 `.md` 后缀),Canvas 全部放进去:
    ```
    doc/xxx/某设计文档.md
    doc/xxx/某设计文档_canvas/某设计文档-架构.canvas
    doc/xxx/某设计文档_canvas/某设计文档-流程.canvas
    ```
    md 中用相对路径嵌入 `![[某设计文档_canvas/某设计文档-架构.canvas]]`,并保留一行 `[[某设计文档_canvas/某设计文档-架构.canvas|打开白板]]` 兜底链接。一个文档只在需要时创建该子目录,不要预建空目录。
  - **禁止**:用 `flowchart`/`stateDiagram`/`architecture-beta` 表达「已判定必须转 Canvas」的复杂图;用 ASCII/截图 表达任何流程图/状态机图/架构图(一律转 Mermaid 或 Canvas)。
  - **架构图统一风格(仅限判定需 Canvas 时,7255 平台)**:共 7 个分层区 = **6 个横向色带**(应用层 L1_APP / 任务层 L2_Tasks / 调度层 L3_RTOS / 服务层 L4_Service / 外设抽象层 L5_EcuAL / 驱动·硬件)+ **右侧 1 个独立竖条**(公共定义层 L6_Public)。
  - **层内内容**:每个色带内放该层真实模块卡片(如 AppsStart、App_Power、App_SocCom、Task_Power、Board、Power、SocComm、UpInf/核心/LowInf 等),卡片写「模块名 + 一句话职责」。
  - **L5 内部箭头**:`UpInf 接口表 → 核心层 → LowInf 接口表 → RTD`,体现三层链;不得跳过 LowInf 直接指到 RTD。
  - **L6_Public 竖条**:注明「被各层引用,不参与依赖方向」,不要画成普通横层。
  - **左侧说明节点**:写「依赖方向:上层 ↓ 下层,层间只走 UpInf / LowInf 函数表」。
  - **颜色按层区分**:应用青(`5`)、任务紫(`6`)、调度红(`1`)、服务绿(`4`)、外设橙(`2`)、驱动黄(`3`)、公共紫(`6`)。
  - **布局**:从上到下分层,卡片对齐网格;组节点置底、卡片置顶;箭头只画真实调用/依赖方向。**尺寸与间距必须满足 `references/canvas-layout.md` 的硬规则**:text 按内容估算尺寸(最小 240×80)、同层水平间距 ≥100px、有边标签的层间垂直间距 ≥140px、group 内边距 40px + 顶部标签 40px。
  - **Canvas 保存前必须校验**:`python scripts/canvas_layout.py check <file.canvas>` 输出 `OK` 才允许保存。流程图/状态机图可先跑 `layout` 初排再人工复核 group 成员与边走向;**固定色带式架构图只用 `check`,禁用 `layout`**(避免打乱人工色带)。边标签 ≤24 units(约 12 汉字);长条件用 **`T1/T2` 短编号 + 图例节点**或写进状态节点正文(Obsidian 边标签无偏移参数,长标签会压节点)。完整规则与来源见 `references/canvas-layout.md`。
  - **边颜色区分单向/双向**:单向边 `"4"`(绿);同一对节点同时有 `A→B` 与 `B→A` 时,两条都 `"6"`(紫)。`canvas_layout.py colorize` 自动分类上色,`check` 校验。
  - **流程图/状态机图**:判定需 Canvas 时同样用节点+箭头表达;时序交互仍用 Mermaid sequenceDiagram,不要混用。

### 4. 版本管理
- 文档头部或尾部有版本号、日期、作者或维护者;设计类文档应有版本历史表格(版本/日期/作者/修改内容/审查人)。

### 5. 与工程一致性(交叉核对)
- 函数名/文件名/分层是否符合当前工程 `doc\README.md` 与架构规范中的硬规则(命名前缀、返回值类型等;dabbox 范例:EcuAL_/Service_/Task_ 前缀、usb_dev_dab_*、Std_ReturnType)。
- README.md 索引相对链接是否指向实际存在的文件;文档引用的代码路径/模块在工程中是否真实存在。

### 6. 技术准确性抽查
- 与当前工程硬约束冲突即为严重问题(dabbox 范例:USB FIFO 总计 320 单元;WDT 时钟源是 PCLK1(100MHz)不是 LRC;Flash 双槽 Bootloader 0x0000-0x8000 / Slot A 0x8000-0x40000 / 标志位 0x40000 / Slot B 0x42000-0x7A000;Std_ReturnType(E_OK/E_NOT_OK);STD_ON/STD_OFF)。
- 其他工程以其根 CLAUDE.md 的 Gotchas 与硬约束为基准。

### 7. 内容浓缩度(激进版硬规则)
- **7.1 以图/表为准**:能用图表达的流程/状态机/架构/时序,正文精简为图+一句结论,禁止大段文字复述图中信息;能用表格表达的参数/清单不用文字罗列;**流程图/状态机图/架构图按 3.4 阈值决定 Mermaid 还是 Canvas(简单图留 Mermaid,命中 no_canvas_docs 一律留 Mermaid),时序图一律 Mermaid sequenceDiagram**;ASCII/text 图必须转换,不得保留。
- **7.2 消灭重复**:同一事实只留一处权威定义,其余改一行链接引用;同一代码实现只在「实现」章节出现一次,其他章节引用;图+表+正文三处说同一件事只留图+表。
- **7.3 合并压缩**:同主题多个小节合并(多个小参数表并入总表、四行「同上」并成一行范围);列表式内容压成表格;章节重排后同步目录与交叉引用编号。
- **7.4 删除废话**:修饰性形容词、思考过程、营销式「集成优势/✓ 优点」列表、无信息量时间状语、人物成就罗列(压成一行);解释性长段落压成要点。
- **7.5 保留项(不可删)**:决策结论与取舍原因(一句话依据)、事实参数(时序/宏名/地址/带宽)、代码路径引用、核心实现代码(注释可行内化)、Canvas 图 / Mermaid 图(含时序图、判定留 Mermaid 的流程图) / 表格、版本信息、待人工确认标注、信息来源署名。
- **7.6 浓缩目标**:正文篇幅压缩 30%-50% 为底线,笔记类目标 45%+;表格/代码块/Canvas 图/Mermaid 图(含时序图)/版本信息不缩。已在前几轮整改过的文件不重复浓缩,仅检查新增内容。删任何一句前自检「删了读者还能不能复现同样的事实」,拿不准的保留并标「待人工确认」。

## 问题分级

- **严重**:时序参数无来源或与硬约束冲突、时序图 t 参数无定义无法回溯、README/文档内链接失效、命名违反工程硬规则、完全缺失版本信息。
- **建议**:章节缺失、代码块未标语言、参数未用表格、时序图缺 participant 声明、未标注参数符号与数值、异步/主动箭头混用、缺 loop/alt 异常分支、未写明采样边沿、信号命名与数据手册不一致、一张图混用多种协议时序、重要延时/超时无文字说明。
- **提示**:格式细节与表述优化项。
- **浓缩类定级**:大段文字重复图/表信息、多处重复定义、ASCII 图未转 Mermaid/Canvas、Mermaid flowchart/stateDiagram 达到 3.4 阈值(≥4 分)未转 Canvas、列表未表格化 → 建议级,直接浓缩;纯表述冗余 → 提示级。简单图留在 Mermaid **不算问题**,不得为转 Canvas 而转。

## 整改执行(直接改,用户要求)

1. 只修改**当前工程 `doc\` 下**的 .md 文件(含 README.md);**允许在 `<文档名>_canvas` 子目录新建/修改 `.canvas` 白板**(仅限 3.4 判定 ≥4 分的复杂图);严禁修改任何源代码、配置文件、图片、.mmd 或其他类型文件。**开工前先读 `[doc_audit]` 三张名单**:命中 `no_modify_docs` 整份跳过,命中 `no_canvas_docs` 全部图保持 Mermaid、禁建 canvas。
2. 每个文件修改前先 Read 全文再精确编辑;保持 UTF-8,不破坏原有 Markdown 结构(注意代码块闭合)。
3. 需核实路径/函数/宏/文件时,在**当前工程根**用 Glob/Grep 检索;部分源码带 `%TSD-Header-###%` 透明加密头,Read 会读到密文,改用 Grep 核实;Grep 对加密文件同样无效时,改用文件存在性检查 + 模块 CLAUDE.md(未加密)间接核实并在报告中注明限制。
4. 补写内容只能从文档现有信息或工程源码推导;无法确定的标「待补充/待实测/待人工确认」,严禁编造。
5. 版本信息统一在文件末尾追加(已有零散版本信息的合并规范化,日期用当天日期):设计类文档用版本历史表(版本/日期/作者/修改内容/审查人,作者王锦、审查人待审查);其他文档简化为三行(文档版本 V1.0.0 / 最后更新 <当天日期> / 维护者 王锦)。README.md 版本历史表追加一行本次整改记录。无改动的文件不追加版本行、不进入报告明细。
6. 具体整改项:
   - 一级标题重复:多余的 `#` 降为 `##`,子标题层级顺延检查。
   - 代码块未标语言:补 c/text/shell/mermaid/protobuf/pseudo(`mermaid` 用于 sequenceDiagram 与判定留 Mermaid 的简单流程/状态/架构图;Canvas 是 `.canvas` 文件,不是代码块)。
   - 时序/寄存器/引脚/参数未用表格:整理为表格并补「来源」列。
   - 设计类文档缺章节:概述(含适用 MCU)、硬件资源、系统架构(按 3.4 选图形式)、软件流程/状态机(按 3.4 选图形式)、时序设计(Mermaid sequenceDiagram)、寄存器或 API 说明、注意事项、测试验证——按可推导内容补写,写不出的标待补充。
   - 时序图不合规:补 participant 声明、Note 参数符号与数值、实线/虚线箭头语义修正、loop/alt 异常分支、采样边沿说明;非 Mermaid 时序图改 Mermaid sequenceDiagram。
   - 流程图/状态机图/架构图不合规:①先按 3.4 打分;**<4 分(简单图)且原为 Mermaid 的保持不变**;②原为 ASCII/截图 的一律改 Mermaid(≥4 分则改 Canvas);③≥4 分(复杂图)且未命中 `no_canvas_docs` 的,在 `<文档名>_canvas/` 子目录新建 `.canvas`,md 中 `![[<文档名>_canvas/xxx.canvas]]` 嵌入 + `[[<文档名>_canvas/xxx.canvas|打开白板]]` 兜底链接,原 Mermaid 块删除;④命中 `no_canvas_docs` 的一律保持/改为 Mermaid,不建任何 canvas。
   - 时序参数表缺失:从正文提取数值建立参数表(参数/符号/最小/典型/最大/单位/来源)。
   - 内容浓缩(激进版):①图/表覆盖的大段正文精简为图+一句结论;②同一事实/同一代码多处出现只留权威处,其余一行引用;③同主题小节合并、四行「同上」并一行、ASCII 状态图/流程图按 3.4 转 Mermaid 或 Canvas(时序图转 Mermaid sequenceDiagram)、要点式列表转表格;④删修饰性废话与营销式列表,人物介绍压一行;⑤代码块注释行内化压缩行数;⑥章节重排同步目录与交叉引用;⑦浓缩后自检事实完整性,拿不准的保留标「待人工确认」。
   - 版本信息缺失:按第 5 条补充。
   - 命名违反硬规则:修正文档描述,不动源码。
   - README 链接失效/目录名错误:修正相对路径,删除指向不存在文件的条目。
   - 文档引用不存在的代码路径/模块:改为实际路径或注明示例代码。

## 输出要求

- 整改完成后,报告作为 doc-audit 章节写入**统一报告文件**(路径规则见 SKILL.md「统一报告文件」;同日已存在则按锚点替换本模式章节)。下述报告结构即该章节内容,不再单独生成 doc_review 文件。
- 报告为**中文 HTML 文件**(纯单文件,表格用 `<table>`,样式内联、无需外部资源,浏览器直接可开),结构:①汇总表(文件|文档类型|严重/建议/提示问题数|整改状态)——全量模式覆盖全部 .md 文件,无问题的记「0 问题/无需整改」,命中 `no_modify_docs` 的记「按配置跳过」;②逐文件整改明细(文件路径、整改项、对应评审条款编号、整改说明、待人工确认项),仅列有改动的文件;③末尾附本次审核范围与依据、三张授权清单的命中情况、所有「待人工确认」清单。
- 报告写完后,仅当存在「待人工确认」的严重项时在执行摘要列出前 3 条,否则一句话说明整改与报告已保存。
- 浓缩整改需在报告中记录每个文件的行数变化(整改前→整改后)。
- 整改中新建/修改的 `.canvas` 白板须在报告中单独列出:路径(含 `<文档名>_canvas/` 相对路径)、对应 md、节点数/边数、替换的是哪类图(架构/流程/状态机)、3.4 打分结果;判定留 Mermaid 的简单图也需在明细中一行说明「得分 n/4,保留 Mermaid」。
- 命中 `no_canvas_docs` 的文档须在报告单列一节:文档路径、命中键、所有保持 Mermaid 的图清单。
- 用户偏好:直接动手整改,给结论、给位置,不客套、不编造。
